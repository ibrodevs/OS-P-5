# OS-P-5 — CPU Scheduling Simulator (Variant B)

Практическая работа по алгоритмам планирования CPU. Реализованы **FCFS, SJF, SRTF, вытесняющий Priority, Round Robin**, метрики, анализ кванта RR и aging для борьбы с голоданием.

## Что реализовано

- единая функция `simulate(processes, algorithm, **params)` возвращает список интервалов выполнения;
- FCFS;
- SJF (невытесняющий);
- SRTF (вытесняющий, проверка новых процессов каждый такт);
- Priority — вытесняющее приоритетное планирование;
- Priority + aging (`aging_interval`);
- Round Robin с настраиваемым квантом;
- метрики:
  - среднее время ожидания;
  - средний оборот (turnaround);
  - среднее время отклика;
  - загрузка CPU;
  - число переключений контекста;
- анализ RR для `q = 1..10` на `set2.txt`;
- SVG-график `rr_quantum.svg`;
- демонстрация голодания и эффекта aging;
- unit-тесты для контрольного `set1` и критического соглашения очереди RR.

## Формат входных данных

```text
PID arrival burst priority
```

Например:

```text
P1 0 8 3
P2 1 4 1
P3 2 9 4
P4 3 5 2
```

Поле `priority` можно опустить, тогда используется `0`. В Priority **меньшее число означает более высокий приоритет**.

## Запуск

Требуемый формат команды:

```bash
python3 sched.py --algo rr --quantum 3 set1.txt
```

Другие примеры:

```bash
python3 sched.py --algo fcfs set1.txt
python3 sched.py --algo sjf set1.txt
python3 sched.py --algo srtf set1.txt --gantt
python3 sched.py --algo priority set1.txt --gantt
python3 sched.py --algo priority --aging-interval 2 set1.txt --gantt
python3 sched.py --algo all --quantum 3 set1.txt
```

`--gantt` печатает интервалы выполнения, например:

```text
SRTF: 0-1:P1 | 1-5:P2 | 5-10:P4 | 10-17:P1 | 17-26:P3
```

## Метрики

Для процесса:

- `turnaround = completion - arrival`;
- `waiting = turnaround - burst`;
- `response = first_start - arrival`.

Загрузка CPU:

```text
CPU utilization = busy_time / total_elapsed_time * 100%
```

Симулятор выводит итоговую таблицу по алгоритму/алгоритмам.

## Проверка set1

Контрольный набор:

```text
P1 0 8
P2 1 4
P3 2 9
P4 3 5
```

Получено:

| Алгоритм | Среднее ожидание | Средний оборот |
|---|---:|---:|
| SRTF | **6.50** | **13.00** |
| RR, q=3 | **13.50** | **20.00** |
| FCFS | **8.75** | **15.25** |

### Важное замечание про FCFS в условии

В тексте задания указан эталон FCFS `9.25 / 15.75`, но для данных `P1(0,8), P2(1,4), P3(2,9), P4(3,5)` стандартный FCFS однозначно даёт `8.75 / 15.25`.

Расчёт ожидания:

- P1: `0`;
- P2: `8 - 1 = 7`;
- P3: `12 - 2 = 10`;
- P4: `21 - 3 = 18`;
- среднее: `(0 + 7 + 10 + 18) / 4 = 8.75`.

Оборот:

- P1: `8`;
- P2: `11`;
- P3: `19`;
- P4: `23`;
- среднее: `(8 + 11 + 19 + 23) / 4 = 15.25`.

Поэтому реализация сохраняет корректное определение FCFS, а обязательные контрольные значения **SRTF и RR(q=3) совпадают с условием точно**.

## Соглашение очереди Round Robin

В задании есть важное правило:

> процесс, прибывший в момент `t`, ставится в очередь раньше процесса, вытесненного в тот же момент `t`.

Оно реализовано явно. После каждого тика RR сначала добавляются процессы, прибывшие в текущий момент времени, и только затем незавершённый процесс после окончания кванта возвращается в конец очереди.

Это отдельно проверяется тестом `test_rr_boundary_arrival_before_requeue`.

### Компромисс RR

Маленький квант делает RR более отзывчивым: каждый процесс быстрее получает CPU, но резко растёт число переключений контекста. В реальной ОС каждое переключение имеет накладные расходы, поэтому слишком маленький квант снижает полезную производительность.

При увеличении кванта переключений становится меньше, но RR постепенно приближается к FCFS: процесс может дольше ждать своей очереди и интерактивность ухудшается. Поэтому квант выбирают как компромисс между отзывчивостью и стоимостью переключений.

В нашем CPU-bound `set2` рост `q` от 1 до 10 уменьшает число переключений с **350 до 43**.

## Priority и aging: демонстрация голодания

Файл `starvation.txt` содержит процесс `LOW` с низким приоритетом и непрерывно поступающие процессы с высоким приоритетом.

Запуск:

```bash
python3 aging_demo.py
```

Без aging:

```text
LOW waiting=45, response=45, completion=51
```

То есть `LOW` не получает CPU, пока не закончатся все высокоприоритетные задачи. В конечном тестовом наборе это длительная задержка; если поток высокоприоритетных процессов продолжать бесконечно, получится настоящее бесконечное голодание.

С aging (`aging_interval=1`) ожидающие процессы постепенно улучшают эффективный приоритет. `LOW` начинает выполняться значительно раньше, поэтому starvation устраняется.

Принцип эффективного приоритета:

```text
effective_priority = base_priority - waiting_time // aging_interval
```

Так как меньшее значение означает более высокий приоритет, долго ожидающий процесс постепенно поднимается в очереди.

## Контрольные вопросы

### 1. Почему SJF нельзя применять в реальной ОС напрямую?

SJF должен заранее знать длину следующего CPU burst каждого процесса. В реальной системе точное будущее время работы процесса неизвестно. ОС может только прогнозировать burst по предыдущему поведению процесса, поэтому чистый SJF напрямую реализовать нельзя.

### 2. Что происходит при кванте RR, стремящемся к бесконечности?

Если квант становится настолько большим, что каждый процесс успевает завершиться за один квант, вытеснений по таймеру больше нет. Round Robin фактически превращается в FCFS: процессы выполняются до завершения в порядке очереди.
